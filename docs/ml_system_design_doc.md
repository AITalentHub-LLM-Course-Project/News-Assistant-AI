# ML System Design Doc - [RU]
## Дизайн ML системы - Бот для суммаризации новостей о СИМ MVP 01

### 1. Цели и предпосылки

#### 1.1. Зачем идем в разработку продукта?

- Бизнес-цель: Создание автоматизированной системы для анализа и суммаризации новостей о самокатах и других средствах индивидуальной мобильности (СИМ)
- Почему станет лучше: Система позволит быстро получать актуальную информацию о новостях в сфере СИМ, что поможет в принятии бизнес-решений и мониторинге рынка
- Что будем считать успехом: Создание рабочего MVP, способного корректно отвечать на вопросы о новостях в сфере СИМ с использованием RAG (Retrieval-Augmented Generation)

#### 1.2. Бизнес-требования и ограничения

- Основные требования:
  - Возможность поиска и анализа новостей по заданным темам
  - Генерация осмысленных ответов на вопросы о новостях
  - Поддержка временных фильтров для поиска новостей
  - Интеграция с Telegram-каналами как источником новостей

- Бизнес-ограничения:
  - Необходимость работы с русскоязычными текстами
  - Требования к скорости ответа системы
  - Ограничения по использованию API GigaChat

#### 1.3. Что входит в скоуп проекта/итерации, что не входит

Входит в скоуп:
- Разработка системы сбора новостей из Telegram-каналов
- Создание векторной базы данных для хранения и поиска новостей
- Интеграция с GigaChat для генерации ответов
- Разработка веб-интерфейса для взаимодействия с системой

Не входит в скоуп:
- Мультиязычность (только русский язык)
- Анализ изображений и видео
- Интеграция с другими источниками новостей
- Система рекомендаций новостей

#### 1.4. Предпосылки решения

- Использование RAG (Retrieval-Augmented Generation) для генерации ответов
- Векторная база данных Chroma для хранения и поиска новостей
- Модель эмбеддингов rubert-tiny-turbo для векторизации текста
- GigaChat как основная LLM для генерации ответов

### 2. Методология

#### 2.1. Постановка задачи

Технически система представляет собой гибридную архитектуру, сочетающую:
- Систему сбора и хранения новостей
- Векторную базу данных для семантического поиска
- LLM для генерации ответов на основе найденного контекста

#### 2.3. Этапы решения задачи

##### Этап 1. Подготовка данных

###### Описание данных/сущностей
- Новостные сообщения из Telegram-каналов
  - Текст сообщения
  - Метаданные (дата публикации, канал, ID сообщения)
  - Ссылка на сообщение в Telegram
- Структура данных в БД:
  - SQLite таблица `news` для хранения исходных данных
  - Chroma для векторного хранилища эмбеддингов

###### Процесс генерации данных
- Источники данных:
  - Telegram-каналы, указанные в переменной окружения TELEGRAM_CHANNELS
  - Фильтрация по ключевым словам: ["самокат", "мобильности", "электросамокат", "кикшеринг"]
- Формат данных:
  - Текстовые файлы с сообщениями из Telegram
  - SQLite для хранения структурированных данных
- Регулярность обновления:
  - Периодический сбор каждые N минут (настраивается через DOWNLOAD_INTERVAL_MINUTES)
  - Синхронизация с векторной БД при каждом запросе

###### Решение проблемы недостаточности данных
- Стратегии:
  - Расширение списка Telegram-каналов
  - Увеличение лимита сообщений при загрузке
  - Настройка фильтрации по ключевым словам
- Требуемый объем данных:
  - Минимум: 1,000 новостных сообщений
  - Оптимально: 10,000+ сообщений
  - Целевой период: последний год

###### Обработка конфиденциальной информации
- Типы конфиденциальных данных:
  - Персональные данные в сообщениях
  - Ссылки на сообщения в Telegram
- Методы обработки:
  - Хранение только публично доступных данных
  - Ограничение доступа к API
  - Безопасное хранение API ключей

###### Необходимый результат этапа
- Рабочая система сбора данных из Telegram
- Структурированная база данных с новостными сообщениями
- Векторное хранилище с эмбеддингами
- Система мониторинга и логирования

##### Этап 2. Подготовка прогнозных моделей

###### ML-метрики и функции потерь
- Метрики качества:
  - Semantic Similarity Score для оценки релевантности ответов
  - Оценка качества ответов на основе контекста
- Функции потерь:
  - Cosine Similarity Loss для обучения эмбеддингов

###### Схема ML-валидации
- Валидационные наборы:
  - Временное разделение (80/10/10)
  - Стратификация по источникам данных
- Метрики валидации:
  - Точность ответов на тестовых запросах
  - Релевантность найденного контекста
  - Время генерации ответов

###### Бейзлайн
- Модели:
  - SentenceTransformerEmbeddings с моделью rubert-tiny-turbo для эмбеддингов
  - Chroma для векторного поиска
  - GigaChat для генерации ответов
- Предобработка:
  - Токенизация и лемматизация
  - Базовая очистка текста

###### Стратегии развития решения
- Модели:
  - Эксперименты с разными моделями эмбеддингов
  - Fine-tuning промптов для GigaChat
  - Оптимизация параметров поиска в Chroma
- Предобработка:
  - Расширенная очистка текста
  - Извлечение ключевых фраз
  - Нормализация текста

###### Анализ и интерпретация
- Методы:
  - Анализ релевантности найденных документов
  - Оценка качества ответов
  - Анализ edge cases
- Мониторинг:
  - Отслеживание качества ответов
  - Метрики производительности

###### Риски и их снижение
- Риски:
  - Качество эмбеддингов для русского языка
  - Ограничения API GigaChat
  - Проблемы с качеством ответов
- Снижение рисков:
  - Мониторинг качества данных
  - Оптимизация промптов
  - Кэширование результатов

###### Необходимый результат этапа
- Рабочая RAG-система с метриками выше бейзлайна
- Документация по архитектуре и процессам
- Набор тестов и валидационных данных
- Мониторинг и логирование

##### Этап 3. Оптимизация RAG-системы
- Улучшение релевантности поиска:
  - Оптимизация системного промпта для GigaChat
  - Настройка количества возвращаемых документов (k=5)
  - Фильтрация по временным меткам
- Оптимизация производительности:
  - Периодическая синхронизация с SQLite
  - Кэширование результатов поиска
  - Оптимизация запросов к Chroma

##### Этап 4. Интеграция и тестирование
- Интеграционное тестирование:
  - Проверка работы FastAPI эндпоинтов
  - Тестирование взаимодействия с GigaChat API
  - Проверка корректности работы с базой данных
- Мониторинг и логирование:
  - Логирование запросов и ответов
  - Мониторинг ошибок и исключений
  - Отслеживание времени выполнения запросов

### 3. Подготовка пилота

#### 3.1. Способ оценки пилота
- Тестирование на реальных запросах пользователей
- Оценка релевантности найденных новостей
- Проверка корректности ответов GigaChat

#### 3.2. Что считаем успешным пилотом
- Корректная работа всех компонентов системы
- Стабильная работа API
- Удовлетворительное качество ответов

#### 3.3. Подготовка пилота
- Настройка логирования
- Подготовка тестовых запросов
- Настройка мониторинга ошибок

### 4. Внедрение

#### 4.1. Архитектура решения
- Backend: Python FastAPI
- Frontend: Streamlit
- База данных: SQLite + Chroma
- LLM: GigaChat API

#### 4.2. Описание инфраструктуры
- Контейнеризация с использованием Docker
- Настройка переменных окружения
- Управление зависимостями через requirements.txt
- Взаимодействие Frontend и Backend через REST API

#### 4.3. Требования к работе системы
- Доступность API и веб-интерфейса
- Корректная обработка ошибок
- Логирование всех операций
- Удобный пользовательский интерфейс

#### 4.4. Безопасность системы
- Защита API ключей через переменные окружения
- Валидация входных данных
- Ограничение доступа к API

#### 4.5. Безопасность данных
- Безопасное хранение данных в SQLite
- Защита векторного хранилища
- Логирование доступа к данным

#### 4.6. Издержки
- Стоимость API GigaChat
- Затраты на хостинг
- Затраты на поддержку

#### 4.7. Integration points

- Telegram API для сбора новостей
- GigaChat API для генерации ответов
- REST API для взаимодействия с фронтендом

#### 4.8. Риски

- Ограничения API GigaChat
- Качество данных из Telegram-каналов
- Производительность при большом объеме данных
- Точность семантического поиска
